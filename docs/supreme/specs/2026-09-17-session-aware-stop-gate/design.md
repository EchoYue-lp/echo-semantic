# Stop 门禁会话差异归属与重入结算

## 问题与目标

当前 Stop 门禁（`hooks/entry.mjs` `stop()`）在仓库存在语义基线时，只按整体 `git status` 是否有差异（`hasChanges`）加是否存在有效预检（`validState`）判断：

- 会话开始前已存在的差异（历史未提交内容、未跟踪文件）会让**纯只读会话**无法结束，反复报"仓库已有变化但没有有效 semantic-preflight 记录"。
- Stop 阻断后没有任何重入出口：两个已安装版本（缓存 0.1.0 与 distribution 0.3.0）均不检查宿主重入标识（`stop_hook_active`），阻断条件不变时每次 Stop 都再次阻断，形成无限循环。
- distribution 版本的 `isRepeatedVerifiedWorktree` 只豁免"此前已验证通过"的相同工作区，不覆盖"从未通过验证"的重复阻断。

目标：让 Stop 门禁按**本轮会话的归属证据**判断，而不是按工作区整体脏度判断；同时对相同失败的重复 Stop 去重，消除自动循环，同时不把放行伪装成验证通过。

已有差异不是默认忽略项，也不能仅因未提交就称为缺陷。首次发现时先盘点并由助手在第一轮主动询问用户；未回答前允许只读、暂停修改和交付，结束只读会话时保留待裁决状态，不制造 Stop 循环。

## 目标行为

### 原生事件与实际编辑仓库绑定（本地修复）

宿主 `cwd` 是会话工作根，不保证等于编辑目标的 Git 根。原生编辑事件先以事件 `cwd` 解释所有目标（包括新增、删除及 Move 两端），识别实际 Git 根；同一次补丁跨多个根或路径含符号链接时整体拒绝。父工作根不是 Git 仓库时拒绝跨根准入，要求在目标仓库打开会话。单仓干净且无会话字段的既有路径兼容；跨根必须有明确一致的原生会话 ID、目标根已有可信起始观察、用户差异裁决及有效任务预检。不从预检、目标路径或其它会话补造观察。

成功准入的编辑，在原生工作根既有 `session-snapshot.json` 的本会话记录内写入至多 8 项 `repositoryBindings`（根、HEAD、taskId），父根自身编辑也登记同一绑定；没有起始观察时只保存 `routingOnly` 记录，读取快照明确排除它。该字段仅路由，不授予修改、删除或接管权限，不新增状态文件或第二权威。Stop/PreCompact 重读绑定、目标 Git 根、HEAD、本会话观察和任务身份，逐仓调用已有结算/继续包路径；失败不消费其它任务状态。父根快照只证明起始观察：父根任务也须本会话成功准入的 task 绑定；未绑定的父预检与继续包保留，不因存在父快照而消费。父根有快照且没有待结算记录时仍执行其只读差异检查。聚合为单个宿主输出，保持失败阻断。宿主重新打开根、HEAD 或绑定失效时须重新建立真实观察，不猜测恢复。

Codex 的 `PLUGIN_ROOT` 与 Claude 的 `CLAUDE_PLUGIN_ROOT` 分别表示规范宿主入口；Codex 可提供 Claude 兼容别名，因此共享入口优先规范 `PLUGIN_ROOT`，不把 Claude 别名存在当作 Claude 证明。插件定位与宿主判断保持一致。Codex 本机 schema 已确认 `SessionStart.source=fork`，matcher 与快照建立覆盖 fork；resume/compact 仍保留原观察和裁决。

验证区分隔离夹具、本机 CLI schema、真实原生事件及 CLI/SDK 原 writer 的现场写入；手动 Hook、人工 resume 或 Stop idle 不能证明原现场恢复。

### 历史引用与完成收据

任务闭包与全项目校验共用既有 `content_at_revision`、引用路径及锚点合同。对象 `observed_at` 或审查场景显式 `revision` 为 Git revision 时，读取该 Git tree；不得要求已退役路径重新出现在当前工作树，也不得用同名当前文件替代历史内容。无效 revision、缺失 blob、错误锚点与不安全路径继续拒绝。当前任务授权的受控删除仍可按既有预检/repair 合同读取 base 内容；历史引用本身不授予删除权。

历史依据按 `revision + path` 分别绑定 blob 内容摘要，加入任务签名，不能用仅按 path 的当前文件映射覆盖。同一当前文件与不同历史 revision 的引用可以同时存在。当前文件的存在、内容和 stat 观察仍独立保存；已删除路径的历史 blob 不能进入当前文件 stat 检查。

repository 收据有历史依据时，既有 `taskEvidenceDigests` 使用 `files` 与 `references` 信封，分别重验当前文件和历史内容；原有纯文件摘要映射保持兼容。task 收据保存 `referenceDigests`，重复 Stop 在复用前通过同一校验器的 `--reference-receipt-check --task-evidence-stdin` 只读入口重验历史依赖。此入口只输出引用检查结果，不能生成任务完成结论或替代首次 task/session/权限检查，不为 task 重入启动全仓扫描。同 revision 因 Git replace 等原因读到不同 blob 时，两种收据均拒绝复用。 旧 task 收据缺少 referenceDigests 时无法证明没有历史依赖，必须拒绝复用并要求新的任务验证；新无历史依赖收据明确保存空映射，继续快速重入。

验收覆盖 task/repository 两种完成范围、历史已删除引用、同 path 多 revision 与当前文件碰撞、历史锚点、失效 revision、无授权删除、当前内容漂移和历史 blob 漂移；额外覆盖真正调用 Hook 的隔离夹具：首次 task Stop 成功、相同输入重入成功、历史 blob 替换后重入拒绝。夹具不是采用方原生事件或已安装插件恢复证据。

### 已批准 checkpoint 的路由续接

成功准入仓库的 `repositoryBindings.headRevision` 是准入时的HEAD。正常提交推进后，不允许仅删除HEAD检查，也不要求额外编辑来刷新绑定。Stop/PreCompact 遇到HEAD变化时，继续使用同一会话记录检查：实际Git根仍等于原绑定根、目标仓原快照存在、原绑定HEAD可恢复且与当前HEAD存在共同Git谱系、当前有效预检仍是原绑定task且base等于当前HEAD、同会话initialChanges已通过官方refresh/decide绑定当前HEAD且策略为adopt/preserve、保护差异检查仍满足。任何一项缺失或不一致均保留原绑定并拒绝续接。

全部已绑定仓库先完成核验，随后只用既有会话运行态API续接路由HEAD；不得改原始起始快照、复制其它会话处置或修改预检。继续进入原有Stop/PreCompact任务验证，路由续接本身不生成成功收据。未刷新/未裁决、旧预检、另一任务/会话、无共同Git历史的HEAD与根变化继续失败关闭。未知会话若只能结束父根的空只读会话，不读取或消费已有子任务，退出0不能充当子仓验证。

正常 PR squash/rebase 后旧任务提交未必是新 main 的祖先，任务分支也可按既定交付流程删除。共同Git谱系只用于拒绝无关仓库/不可恢复输入，不能单独授权HEAD切换；授权仍来自该会话已确认的当前HEAD处置、同任务当前预检及保护内容核验。不得要求保留任务分支或增加无意义编辑。真实Git回归构造任务两commit、squash main、相同结果tree和删除任务分支，先证明旧祖先条件拒绝，再核对已确认续接通过与未确认HEAD/待裁决/旧PF/错误task继续拒绝。

### 1. 会话起始快照

SessionStart 按**规范化会话 ID + 仓库根**记录会话起始快照，写入 `.echo-semantic/` 运行态（经 `project-state.mjs` 的 `RUNTIME_STATE_FILES` 与 `info/exclude` 机制，不进版本控制）。Codex、Claude Code 使用 `session_id`；Cursor 的 SessionStart 使用 `session_id`，Stop 使用与其等价的 `conversation_id`。Codex、Claude Code 只在 startup/resume/clear 时重录快照；Cursor 没有 `source` 字段，每次 SessionStart 都记录当前会话快照。快照覆盖：

- HEAD 提交标识；
- `git status --porcelain=v1 -z --untracked-files=all` 的原始输出、HEAD、索引 blob 元数据和已有差异路径的内容指纹；
- 仓库根路径与 worktree 身份。

快照只回答"会话期间工作区内容是否发生了变化"，**不证明已有差异经过语义验证**。同一运行态文件按会话键控保存多条记录；不同会话、不同仓库根的快照互不覆盖或复用。记录更新必须串行执行 read-modify-write 并原子替换，避免并发 SessionStart 丢失其它会话；快照保留 7 天、去重记录保留 24 小时，并各自只保留最近 128 个会话，写入时清理过期记录。

### 2. Stop 判定矩阵

| 情况 | 行为 |
|---|---|
| 初始已有差异且尚未裁决，内容未变化 | 允许只读结束；保留"待裁决、未验证"及待结算记录；不生成成功收据、不触发 followup |
| 用户选择保留或只读，受保护的初始差异未变化且没有本轮待结算修改 | 允许结束；注明已有差异被保留但未验证；不生成成功收据 |
| 用户接管指定已有差异 | 仅指定范围解除保护；仍按有效预检与完整验证结算，不能仅因指纹一致放行 |
| 有可信快照，检测到新增变化（任何哈希输入变化）或本轮待结算修改，但没有有效预检 | 阻断，指明缺少预检依据 |
| 有变化且有有效预检 | 现有验证流程不变；通过后按现有方式记录收据 |
| 起始快照缺失、损坏，或当前仓库根与快照登记不一致 | 状态写明"无法判断、未验证"，**允许结束**；不补造快照，不生成通过收据 |

写前预检门禁（PreToolUse `checkEditScope`）在已有范围检查前增加差异处置检查：未裁决或选择只读时拒绝写入；选择保留时拒绝触碰已有差异；接管时仅用户指定路径解除保护。普通预检不能代替用户裁决，也不得在 Stop 自动补写修改前记录。快照只能证明内容变化，不能可靠认定修改者；归属未知时如实说明，不一律归因于当前助手。

### 5. 已有差异首次处置

- SessionStart 盘点暂存、未暂存、未跟踪差异、路径及当前验证收据是否匹配，不读取或展示完整敏感内容。Hook 把事实与待裁决指令注入助手上下文，助手在第一轮请求用户选择，不由 Hook 假装直接完成提问。
- 策略为接管指定差异、保留已有差异并仅处理本轮范围、暂停修改仅只读。接管须指定初始差异路径，未选路径继续受保护；保留和只读不表示验证通过，任何策略都不授予 stage、commit、discard、cleanup 或发布权限。
- 用户明确回答后由专用记录入口将其原话依据、会话 ID、仓库、初始指纹和选择写入同一快照；入口必须比较询问时的指纹，差异已变则拒绝旧答复、重新盘点询问。提示注入不作为用户答复证据，不自动选择默认策略。
- 裁决按会话与仓库隔离，resume/compact 保留未变化的裁决和初始差异，不重新把未结算修改视为旧差异。HEAD 或受保护初始差异变化使裁决失效，需要新询问；本轮新增路径不导致无关裁决失效，已接管路径在有效预检范围内的预期修改仍走通常验证流程。
- 同一待裁决观察只在上下文中请求一次；Stop 不重复拉回助手。未经裁决的新增修改、保护路径变化或选择只读后修改首次阻断，相同失败重入去重但保留未验证状态。快照或内容观察不可用不生成裁决/成功收据。
- 确定性检查只覆盖真实宿主 Hook 能观察到的写入与停止路径；Skill 要求所有写入和交付前先处理待裁决状态，不能把 Skill 指令称为机器门禁。CI 继续独立验证最终提交，不把会话策略当作通过证据。

### 3. 重复失败去重

首次因"缺少预检依据"阻断时，记录去重键：**会话 ID + 仓库根 + 当前内容指纹 + 失败原因 + 结算证据指纹**。Codex、Claude Code 用 `stop_hook_active` 标识重入；Cursor 用大于零的 `loop_count` 标识重入。满足全部条件时：

- 不再次阻断；
- 保留"验证未通过/待处理"状态；
- 不清除预检或待结算记录；
- 不生成通过收据。

内容指纹、预检记录或验证证据任一变化后，重新按第 2 节矩阵判定。该豁免不跨会话、不跨仓库、不迁移到"验证通过"语义。

### 4. 失败场景

- **会话中修改了本已脏的文件**：porcelain 路径状态可能不变，但已有差异路径的内容指纹会变化 → 识别为新变化 → 走阻断路径。仅暂存区变化由索引 blob 元数据覆盖。
- **验证失败后补齐证据重试**：预检记录更新 → 去重键失效 → 重新执行验证，通过后才结算。
- **父仓/子仓切换**：仓库根参与快照与去重键，不串用。
- **会话恢复（resume）**：resume 时重录快照；此后按新会话起点判断。
- **并发会话与修改**：各会话保留独立快照和去重记录；任一会话观察到内容变化时都按自己的快照结算。内容归属未知时状态如实标注，不自动归因，也不因另一会话启动而丢失快照或自动放行。

## 范围与非目标

范围：共享 Hook 的 session-start/pre-edit/stop、现有会话快照与指纹、差异裁决记录入口、semantic-preflight 指令、状态投影及定向测试；无需新增宿主事件。

非目标：

- 不修改 `semantic-preflight` Skill 合同与 `preflight.py` 记录格式；
- 不把已有差异补记为已验证；
- 不引入会话外的常驻服务或遥测；
- 不在本次设计中处理安装缓存与 distribution 的发布同步（实现后另行发布）。

## 系统边界

- 快照与去重记录是**会话级运行态**，权威仍是采用方 Git 仓库与 `.echo-semantic/` 运行态目录；不新增第二套状态权威。
- 快照指纹复用 Git HEAD、porcelain 与索引元数据，只读取 porcelain 已报告的差异路径来区分本已脏文件的后续变化，不扫描或读取无差异文件；文件内容只进入内存中的摘要计算，不写入运行态或日志。语义对象（baseline、Finding 等）验证仍由 `semantic-verify` 校验器承担。
- 脏 submodule 的 nested Git 必须绑定已打开并验证的目录身份，不能使用先前检查过的可变路径。POSIX 复用现有 `python3` 标准库 `fchdir` 后执行 Git；没有可靠目录 fd 或 `fchdir` 能力时不执行 nested Git，指纹如实为不可用，不走路径 fallback。

## 核心结构与数据流

```text
SessionStart
  → 规范化宿主会话 ID
  → project-state 串行更新 session-snapshot 中该会话记录
  → 初始已有差异且未裁决：注入首轮询问指令

用户明确回答 → 核对观察指纹 → 将策略写入同一会话快照
PreToolUse(Edit|Write) → 差异处置/保护检查 → 现有预检范围检查

Stop:
  无基线 → 现状放行
  按会话 ID + root 读快照
    待裁决且只读 → 保留待裁决、未验证并结束，不重复 followup
    未授权修改 → 首次阻断，相同失败重入去重
    缺失/损坏/root 不匹配 → 状态"无法判断、未验证"，放行（无收据）
    指纹一致且无待结算 → 状态"本轮无修改"，放行（无收据）
    指纹变化或待结算
      有有效预检 → 现有 uv verify 流程 → 通过则收据+清态
      无有效预检
        去重键命中（同会话/同指纹/同原因，宿主重入）→ 状态"待处理"，放行（无收据）
        否则 → 阻断并记录去重键
```

## 设计方案与关键取舍

- **组合指纹而非全仓内容哈希**：porcelain 覆盖差异路径但不能区分本已脏文件的后续内容变化；索引 blob 元数据覆盖暂存变化，已有差异路径的内容摘要覆盖工作树和未跟踪文件变化。只处理已有差异路径，避免读取全部仓库或依赖 mtime。
- **快照缺失时放行而非阻断**：无法区分"旧会话恢复"与"宿主未提供会话标识"；阻断会重演只读误拦。代价是极端情况下绕过一次完成验证，由写前预检兜底实际修改。
- **去重键绑定内容指纹**：内容不变才豁免重复阻断；任何新修改立即恢复阻断能力，避免"一次阻断永久放行"。
- **同文件按会话键控**：保留两个既有运行态文件，在文件内保存有界会话记录；通过 repo-local 短期锁和原子替换避免并发覆盖，不引入数据库、常驻服务或第二状态权威。

## 复用与实现约束

1. `runtime/project-state.mjs` 已有运行态文件白名单、原子写与 `info/exclude` 机制：`session-snapshot.json`、`stop-dedupe.json` 继续作为固定运行态文件；新增串行更新能力，不引入新存储。
2. `runtime/route.mjs` 已计算 `worktreeDigest`/`worktreeFingerprint`：快照哈希直接复用该计算，不另起炉灶。
3. 宿主字段以官方合同和当前 CLI 为准：Codex、Claude Code 使用 `session_id`/`stop_hook_active`，Cursor 在 Stop 使用 `conversation_id`/`loop_count`；适配层归一化后再进入共享判定。
4. 无需新增包依赖、数据库或常驻进程；摘要使用 `node:crypto`，POSIX nested Git 复用现有 `python3` 标准库目录 fd 能力，能力缺失时保守退化为指纹不可用。

## 验收标准

在 `tests/hooks.test.mjs` 补充以下场景，全部通过后设计视为落地（实现另行执行）：

1. 已有脏工作区（含未跟踪文件），会话内只读 → Stop 放行，无通过收据。
2. 修改本已脏的文件 / 新增未跟踪文件 / 仅暂存区变化 → 指纹变化被识别。
3. 新变化无预检 → 首次阻断。
4. 相同失败的重入 Stop（`stop_hook_active`）→ 不再阻断，失败状态保留，无收据。
5. 重入期间内容再次变化 → 恢复阻断。
6. 预检补齐后重试 → 走完整验证，通过才结算。
7. 快照缺失 / root 不匹配 / 会话切换 → "无法判断、未验证"并放行，不串用快照。
8. Cursor 使用官方 SessionStart/Stop payload → 正确建立快照、首次返回 followup、相同失败重入不重复 followup。
9. 会话 A、B 交错启动和 Stop → 各自快照与去重记录都可读取；B 不覆盖 A，内容变化后不会因并发自动放行。
10. 大仓库或含干净 submodule 的仓库 → 指纹不读取无差异文件，不因 submodule 存在退化为 `null`。
11. 首次已有暂存/未暂存/未跟踪差异 → 第一轮询问策略；未答复拒绝写入，只读 Stop 不循环且保留待结算记录。
12. 用户保留已有差异 → 本轮新路径可按预检修改，已有路径不得修改；接管指定路径 → 仍须预检并完整验证；只读策略 → 拒绝所有写入。
13. 旧观察指纹的答复、跨会话答复、HEAD 或保护路径变化 → 不能复用裁决；resume/compact 不静默丢失策略。
